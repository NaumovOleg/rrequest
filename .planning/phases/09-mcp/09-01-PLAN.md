<objective>
Stand up the MCP server foundation: opt-in settings checkbox, a data/action port
built over the existing stores and router, a hardened loopback Streamable-HTTP MCP
endpoint, and the runtime that starts/stops it in response to the checkbox. Prove
end-to-end with a single trivial tool (`about`) so an MCP client can complete the
handshake.

Purpose: the plumbing every future tool hangs off, with the server off until the
user checks the box.
Output: toggling `rrequest.mcpEnabled` starts a reachable, authenticated MCP
server; toggling it off stops it; no new install for the user.
</objective>

<execution_context>

- **Why HTTP, not stdio.** The extension host is already a running process; an
  MCP client cannot `spawn` it as a stdio server. So the extension hosts a local
  HTTP server and the client connects by URL. `StreamableHTTPServerTransport`
  from `@modelcontextprotocol/sdk/server/streamableHttp.js` speaks to Node's
  `IncomingMessage`/`ServerResponse` directly — **use `node:http`, do not add
  express**. Read and JSON.parse the body ourselves; pass it as the third arg to
  `transport.handleRequest(req, res, body)`.
- **Stateless.** For every POST create a fresh transport with
  `sessionIdGenerator: undefined, enableJsonResponse: true`, connect the shared
  server instance, handle the request. GET/DELETE (session ops) aren't needed
  stateless → reply 405. No session map.
- **Where the data lives.** `ensureBootstrap` (panel.ts) constructs the stores,
  reads `rrequest.activeWorkspaceId` from `globalState`, builds the Hub, and owns
  `hub.dispatch`. Build the `McpPort` there and stash it in a module ref
  (`mcpPortRef`) exported via `getMcpPort()` — the same deferred-ref pattern as
  `syncControlRef` / `syncRuntimeRef`.
- **Writes go through the router, not the stores.** `McpPort.dispatch(msg)` calls
  `hub.dispatch('mcp:<unique>', msg)`. That reuses the read-only (viewer) guard,
  the `afterDispatch` → `schedulePush` sync hook, trash handling, and the snapshot
  broadcast. A second write path over the stores would silently break sync.
  Capture the messages posted back to the `mcp:<id>` sink (the snapshot broadcast
  reaches it) so write tools can read the resulting state — implemented as a
  small capture-sink helper in bootstrap.
- **Do not force bootstrap when disabled.** Only call `ensureBootstrap` when the
  server is starting (or a panel/sidebar is opened, as today).
- **Config checkbox.** A `boolean` in `contributes.configuration` renders as a
  checkbox under the "RREQUEST" section the gear opens. No custom webview UI.
- **Bundling.** Everything runtime is bundled (`.vscodeignore` excludes
  node_modules from the `.vsix`). Put `@modelcontextprotocol/sdk` and `zod` in
  `devDependencies` (like `@grpc/grpc-js` / `ws`) so esbuild inlines them.
- **No send tool in v1.** The port does not expose `sendRequest`; sending stays in
  the webview. This removes the SSRF surface entirely.
  </execution_context>

        `server.on('error')` → reject start, mapping `EADDRINUSE` → "port N in
