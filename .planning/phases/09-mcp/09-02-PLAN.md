<objective>
Make collection access an explicit, user-approved act. Add the per-resource grant
store, the `request_access` tool that raises a native Allow/Deny modal, and the
gate every scoped tool runs through — then the read tools that produce the data.

Purpose: satisfy the security requirement that the agent always asks for access
to a collection, enforced at the tool layer (not merely requested in a prompt).
Output: an agent can discover collections, request access, and read their
contents only after the user allows it.
</objective>

<execution_context>

- **Access is per resource, one mechanism.** `access.ts` keys grants by
  `resourceType:id` where type is `workspace` | `collection` | `environment`.
  Different resources never share a grant: a collection grant does not grant
  environment access, and a workspace grant (needed to _create_ a new collection,
  see 09-03) does not grant access to the contents of any existing collection.
- **The prompt is injected**, so `access.ts` is pure/testable:
  `new McpAccess({ prompt, onChanged })`, where `prompt(req)` returns
  `'allow' | 'allow-write' | 'deny'`. Production wires it to
  `vscode.window.showInformationMessage(msg, { modal: true }, ...)`; tests inject
  a stub.
- **Session-scoped by design.** Grants live in an in-memory map created on
  `start()` and cleared on `stop()`. This is what makes "always asks" true across
  reloads/toggles. (`// ponytail: session-scoped; add persistence only if users
ask for it.`)
- **The gate returns a structured denial** the model can act on, e.g.
  `{ ok: false, reason: 'access_required', resource, hint: 'call request_access' }`
  — so the client can retry after asking. A silent empty result would just stall.
- **Metadata vs contents.** `list_collections` returns names/ids only (so the
  agent knows what it may ask for) and is NOT gated; every tool that returns a
  collection's contents or mutates it IS gated. Workspace listing is global and
  ungated (workspaces aren't collections).
- **Environments are read redacted + separately gated**; secret `value`s are
  never returned (the port already strips them). No MCP write of environment
  values in this plan (that is 09-03, and secret values are never writable).
  </execution_context>

  <name>Access store + gate</name>
  <files>src/extension/mcp/access.ts (new), test/mcp/access.test.ts (new)</files>
  <action>
  - `type ResourceRef = { type: 'workspace' | 'collection' | 'environment'; id: string; name: string }`.
  - `type Grant = { write: boolean; at: number }`.
  - `class McpAccess`:
      - `constructor(private opts: { prompt: (req: ResourceRef & { write: boolean; alreadyRead: boolean }) => Promise<'allow' | 'allow-write' | 'deny'>; onChanged?: (grants: { ref: ResourceRef; grant: Grant }[]) => void })`.
      - `has(ref, mode: 'read' | 'write'): boolean`.
      - `async require(ref, mode): Promise<{ ok: true } | { ok: false; reason: 'access_required'; hint: string }>`:
        - if `has(ref, mode)` → `{ ok: true }`.
        - else call `prompt({ ...ref, write: mode === 'write', alreadyRead: this.has(ref, 'read') })`.
        - `'allow'` → grant read; `'allow-write'` → grant write; `'deny'` → remember a **denial** (so we don't re-prompt on every call in the same session) and return `{ ok:false }`.
        - Set `write` grant implies read.
      - `revoke(ref)` / `revokeAll()` / `list(): { ref; grant }[]` / `clear()`.
      - Denials tracked in a separate `Set<string>`; `require` checks it and returns `access_denied` without re-prompting.
  - Tests: allow → subsequent require ok; deny → returns access_denied and prompt called once; write request after read grant → prompts for upgrade; `clear()` drops everything.
  </action>
